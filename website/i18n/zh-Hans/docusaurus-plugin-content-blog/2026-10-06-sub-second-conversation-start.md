AstraBox 把大家已经在用的 Agent 程序（Claude Code、Codex、Pi、DeepSeek
Harness）跑成云端 Agent。每个对话运行在沙箱里，沙箱里跑的是厂商自己的程序。
从零启动这一整套要 8 到 15 秒：创建容器，等命令守护进程起来，挂载工作区，安装
Skills 和 Plugins，克隆仓库，启动 Agent 程序并等它初始化完。

打开预热之后，新对话一秒内就绪：在一台空闲的 8 vCPU 云主机上是 0.40 到 0.50
秒，从收到创建请求算到对话的 READY 事件。做法是把启动的大部分工作放到有人来之前
做完。

<!-- truncate -->

| 引擎 | 创建请求到 READY |
| --- | --- |
| Claude Code | 0.41–0.46 s |
| Pi | 0.41 s |
| Codex | 0.45–0.46 s |
| DeepSeek Harness | 0.49–0.50 s |

*2026-10-06 测量，每个引擎四次，在服务端内部计时。机器是一台空闲的 c6a.2xlarge
（8 vCPU，16 GiB），跑 Docker Compose 部署：Docker 29.1.3 及其默认的 containerd
镜像存储，OpenSandbox server 0.2.3，execd v1.1.0。文中的改动随 AstraBox 0.1.4
发布。Codex 在服务重启后的第一次领取用了 0.92 s。冷启动的范围来自 2026-09-23
的另一次测量（四个引擎 8.2 到 14.6 s）。沙箱跑在 Docker 上，Kubernetes 没有测。*

机器旧、负载高的时候会慢一些。在一台 2016 年的虚拟机（12 vCPU，Xeon E5-2680
v4）上，机器同时还跑着别的任务，用 quickstart 命令装的 0.1.14 正式版里，Claude
Code（0.64 到 0.82 s）和 Pi（0.68 到 0.95 s）仍在一秒内，Codex 是 1.03 到
2.26 s，DeepSeek Harness 是 1.00 到 3.05 s。这是 2026-11-10 每个引擎五次的结果，
从发出创建请求算到 Session 被记为 READY。

## 按依赖对象拆分启动工作

冷启动里几乎没有哪一步依赖对话本身。容器镜像、模型和网关、系统提示词、MCP
服务器、Skills 和 Plugins、默认仓库，还有 Agent 程序自身的启动，都是 Agent 的属性。
属于对话的只有几样：它是给谁的，可以用哪些凭证，文件和对话记录存到哪里。

所以我们在有人来之前，就按 Agent 的完整配置把沙箱准备好，默认每个 Agent 一个：

| 提前准备，按 Agent | 领取时绑定，按对话 |
| --- | --- |
| 沙箱本身，按 Agent 的镜像、网络策略和资源创建 | 对话的身份和所有者 |
| 沙箱出口保险库里的凭证占位符 | 占位符背后、只属于这个对话的模型网关密钥 |
| Skills、Plugins、默认仓库，以及（配置了工作区卷时）一个工作区视图 | 对话的持久工作区，接入这个视图；对话记录的存放位置 |
| Agent 程序，启动到等待对话的那一步 | 这个用户的平台 MCP 路由 |
| 各引擎自己的工作：Codex 的 app server、Pi 停驻的子进程、DeepSeek Harness 的原生对话及其模型路由 | 通过程序自己的通道激活 |

用户只需要等右边这一列。

准备好的沙箱来自 OpenSandbox 的客户端沙箱池，池的状态存在 Redis 里。从池里取箱
是一个原子操作，要么拿到沙箱，要么立刻得知池是空的。池空时对话走冷启动，并把
没命中的原因记进日志。

提前准备带来三个问题。对话的文件要出现在一个先于对话创建的沙箱里。准备好的沙箱
不能服务于一个之后改过配置的 Agent。一个还没有主人的沙箱里不能放任何人的密钥。

## 把持久工作区接进一个已经存在的沙箱

对话比沙箱活得久。沙箱可能在空闲时被回收，可能随节点一起丢失，也可能在崩溃后被
替换，下一条消息会借用另一个沙箱。部署配置了工作区卷时，对话的文件存在这个卷上，
放在平台生成的工作区 id 之下，所有服务于这个对话的沙箱都得在 `/workspace` 看到
同一批文件。

这和预热冲突。准备沙箱的时候没人知道它将来给哪个工作区用，而容器的挂载在创建时
就定死了，Docker 和 Kubernetes 都不能给运行中的容器加卷。领取之后再建沙箱，预热
省下的那几秒就还回去了。把文件拷进去，每次启动都变成一次传输，还多出两份副本
要对账。

AstraBox 给每个准备好的沙箱的是一个工作区视图，而不是工作区本身。视图是一个
单分支的 [mergerfs](https://github.com/trapexit/mergerfs) FUSE 挂载，由沙箱外
一个有特权的小助手进程维护：Docker 上是一个容器，Kubernetes 上是一个 Pod。我们用
mergerfs 只为一个特性，而且和“合并”无关：它的分支可以在运行时更换，不用卸载，
只要往挂载点控制项上写 `user.mergerfs.branches` 这个扩展属性。

沙箱挂载的是视图下的一个子目录，从不挂视图的根。池创建沙箱时，视图指向一个全新的
空工作区，新对话在领取时直接接手这个工作区。已经有工作区的对话（之前的沙箱被回收
或丢了）则要切换视图：AstraBox 让助手把视图指向对话的工作区，助手写入新分支并
读回确认，沙箱接下来在 `/workspace` 下的 `open()` 就落在这个对话的文件上。沙箱、
它的挂载和已经准备好的 Agent 程序都不用动。

视图把目录项、属性和负查找的缓存都设为零，关掉目录缓存和回写缓存，文件内容走
直通 I/O，所以切换之后的下一次查找看到的就是新文件。

切换之前打开的文件描述符仍指向原来的文件，所以视图不会在对话使用期间切换。一个
视图只在领取时绑定一个对话，拒绝第二次绑定。

沙箱没法自己改指向。控制项在 FUSE 挂载的根上，而沙箱只能看到子目录，所以沙箱里
的 root 也碰不到决定它文件的那个控制项。

绑定做到一半崩溃是可以恢复的。助手在动挂载之前先记下这次绑定，以及它要替换的
旧映射。恢复时它只接受旧映射或新映射，重做一次绑定即可完成。

Agent 程序启动之前，AstraBox 会检查 `/workspace` 是一个挂载点，而且就是那个
mergerfs 视图。工作区挂载没到位的沙箱会把文件写到一块随沙箱消失的盘上，所以这样
的候选沙箱直接销毁。

底层的卷可以是本地目录，也可以是 Amazon EFS、NFS 这样的共享文件系统。用共享
存储时，对话可以在另一个节点的沙箱里继续。端到端测试会为一个对话领取准备好的
沙箱，写入文件，换掉沙箱，然后检查下一个准备好的沙箱提供的是同一个工作区 id、
内容逐字节一致，检查控制项在沙箱内无论以 root 还是 Agent 的用户身份都不可见，
并在跨主机的用例里检查替换的沙箱确实跑在另一个节点上。

工作区卷是可选的。没有配置时，上面这些都不会运行：每个 Agent 程序的原生会话保存
在平台数据库里，并恢复到下一个沙箱，所以对话在沙箱丢失后仍能继续，但工作区里的
文件会随沙箱一起丢失。

## 准备好的沙箱只对构建它的那份 Agent 配置有效

按昨天的系统提示词准备的沙箱启动很快，然后以错误的 Agent 身份回答，这比启动慢
更糟。

每个准备好的单元都带一个运行代号（runtime generation）：对构建它所用的全部输入
做的哈希，包括镜像、引擎、沙箱的租用方式和权限级别、网络策略、模型及其网关和
凭证形态、系统提示词、MCP 服务器、Skills、Plugins、引擎选项和 Vault 绑定。领取时
把 Agent 当前的代号和单元的代号做比较，不一致就拒绝。修改 Agent 会轮换它的池，
下一个准备好的沙箱就按新配置构建。Codex、Pi 和 DeepSeek Harness 在激活时还会
比对进程启动参数的指纹。

## 密钥不进准备好的沙箱

准备好的沙箱先于任何对话存在，所以它不可能持有对话的凭证。Agent 程序看到的始终
是占位符。真正的凭证放在沙箱前面的出口保险库里，由它在发往允许主机的请求中把
占位符替换掉。

领取时，如果模型端点支持按对话签发凭证（内置的 LiteLLM 网关支持），AstraBox 会
为这个对话签发一个，并把沙箱的占位符指向它。准备好的进程继续运行，沙箱里什么都
不用重启。模型用量从此记在这个对话名下，而不是记在 Agent 共用的准备阶段密钥上。

## 领取要么激活准备好的单元，要么失败

准备好的单元激活失败就被丢弃，对话的启动随之失败并给出原因。它不会在同一个请求里
回退到冷启动。静默回退会把一个坏掉的准备沙箱变成每次都莫名其妙慢十秒的启动，
而日志里没有任何线索。补充沙箱池是另一个任务，在失败之后运行。

## 关键路径上只留对话需要的事

剩下的大多是记账。单看每一步都不大，但在这次优化之前，它们加起来让 Claude Code
要 1.2 秒左右，DeepSeek Harness 要 1.65 秒。省下的时间主要来自三处改动。

恢复工作现在只在确实有东西要恢复时才运行。启动命令可能在创建或领取沙箱之后、
记录下来之前死掉。同一条命令再次执行时得把那个沙箱找回来，而找回来意味着列出
后端的所有沙箱。但只有重新执行才可能找到东西，因为每条启动命令的 id 都是新的。
所以第一次执行在碰沙箱后端之前，先用一次比较并交换把自己记在 Session 上，然后
跳过列表。重新执行时看到这条记录，才去做查找。

清理工作放到用户被服务之后。领取沙箱会把对话追加到 Agent 的网关密钥账本里。清理
这个账本（读出所有已结束的对话并删除它们的网关密钥）改成领取之后的后台任务，
不再挡在领取前面。

领取路径上不在沙箱里执行命令。在这里，沙箱里每执行一条命令大约要 235 ms，因为
命令守护进程在命令结束后还会把输出流保持打开一小段时间来排空。通过沙箱的文件
API 写一个私有文件大约 5 ms。DeepSeek Harness 在领取时需要一个按对话的状态文件，
用四条命令写要 941 ms，用一次文件调用只要几毫秒。准备好的沙箱里从来没有过这个
文件，程序也只在被请求时才读它，所以这条路径上用不着原子替换那一套。

逐个测量往返的时候还发现一件事，自己跑 Docker 的人值得知道。在 Docker 29 默认的
containerd 镜像存储下，一次 image inspect 大约要 100 ms，和 API 版本无关，而
container inspect 大约 1 ms。OpenSandbox 的 Docker 运行时每次描述沙箱都会
inspect 镜像，为的是报告它的第一个 tag。AstraBox 内嵌的 OpenSandbox server 改为
报告创建容器时用的引用，也就是创建请求里指定的那个镜像。

## 剩下的时间花在哪里

以 2026-10-06 测量中一次约 0.42 s 的 Claude Code 领取为例：

| 步骤 | 耗时 |
| --- | --- |
| 创建 Session 及其启动命令（持久化写入） | ~80 ms |
| 启动记账、代号检查、首次执行记录 | ~45 ms |
| 从池里取箱，含租约续期 | ~40 ms |
| 接手沙箱：读取领取凭据、建立连接、为 Session 重新打标 | ~60 ms |
| 对话凭证：账本条目、网关密钥、保险库更新 | ~40 ms |
| 这个用户的平台 MCP 路由 | ~20 ms |
| 激活准备好的程序 | ~5 ms |
| 记录 READY 并通知订阅者 | ~40 ms |

激活的耗时因引擎而异：Claude Code 约 5 ms，DeepSeek Harness 最多约 90 ms，因为
它要重新接入准备好的原生对话，并在上面选定 Agent 的模型。

还有两个方向可做。领取可以变成一步：表里剩下的、不依赖对话的部分都挪到准备阶段，
彼此独立的步骤并发执行。第一条消息也完全不必等：平台已经为每个对话维护一个持久
的输入队列，在对话启动期间就接受输入，剩下的启动时间就藏在用户打字的时间里了。

## 预热的成本

每个 Agent 保持的空闲准备沙箱数量等于它的预备容量，默认是 1，设为 0 即关闭预热。
在 Docker 主机上，一个空闲的准备沙箱大约占 0.5 GiB（Claude Code）或 0.45 GiB
（Pi），出口 sidecar 另占约 60 MiB，CPU 占用为单核的 2% 到 5%。在 Kubernetes
上，调度器会为对话沙箱预留它的 requests，即 250m CPU 和 1 GiB。对话领走一个沙箱
之后，池会再准备一个补上；空闲的沙箱在沙箱租约到期时回收。详见
[容量规划](/zh-Hans/docs/deploy#plan-capacity-for-prepared-sandboxes)。
